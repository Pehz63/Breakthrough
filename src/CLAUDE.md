# src/ Reference

Engine, evaluators, search, ML system, and ranking internals. Loaded when
working on files in `src/`. The always-loaded overview and build commands
live in the root `CLAUDE.md`.

## File details

| File | Purpose |
|---|---|
| `globals.h` | Master header: macros (`EMPTY='.'`, `WHITE='W'`, `BLACK='B'`, `SIZE=8`), enums, `extern` globals, and all function prototypes. Included by every `.cpp`. |
| `globals.cpp` | Definitions of all global variables (`board`, `g_whiteCount`, `PRNT`, etc.). Separated from `main.cpp` so the test executable can link them without pulling in `main()`. |
| `main.cpp` | Top-level game loop: seeds RNG, loads board, calls `getSettings()`, dispatches turns, tracks per-player time, and accumulates scores over multi-game sets. Holds per-side `wEval`/`bEval` (evaluator index) and `wParams`/`bParams` (`int[MAX_EVAL_PARAMS]`). It also hosts parameter test-sweep mode (`testingParam` 1 = depth, 2..1+paramCount = the tested side's evaluator weights). When `SHOW_EVAL` is set, after each move it prints that side's eval via `printEvalLine()` (`now=` immediate static eval, plus `pred=` predicted best-line eval for MiniMax sides); `formatEval()` renders forced wins as `+WIN`/`-WIN`. |
| `board_io.cpp` / `board_io.h` | Board file I/O and display: `getBoard()`, `reloadBoard()`, `printBoard()`, `loadMinimaxParams()` (reads `<side>_eval`, `<side>_depth`, `<side>_opener`, and each evaluator param via `<side>_<key>`, falling back to legacy `<side>_<key>_weight` names) |
| `settings.cpp` / `settings.h` | Interactive CLI configuration. `getSettings()` prompts for player types and, for MiniMax, the evaluator and its weights (looped from the registry by name via `getEvaluatorSettings()`); also game count, verbosity, and `SHOW_EVAL` (the "Show board evaluations?" prompt). Unset weights awaiting a prompt must be seeded with `EVAL_PARAM_UNSET` (globals.h, INT_MIN), not -1: the prompt loop skips any param already inside its [lo, hi] registry range, and evaluators with negative minimums (Advanced) make -1 a valid value. `printVictor()` displays winner and timing. |
| `moves.cpp` / `moves.h` | All move logic: dispatch (`moveWhite`/`moveBlack`), human input parsing, full validation (`tryMoveWhite/Black`), fast AI validation (`tryMoveQuickWhite/Black`), execution (`playMoveWhite/Black`), reversible simulation (`simulateMove`/`unsimulateMove`). `simulateMove`/`unsimulateMove` also maintain the incremental positional accumulator `g_evalPos` (via `evalPosLocal`) when `g_evalIncremental` is set, the per-row piece counts `g_rowCountW/B` (3 counter bumps per move) when `g_evalRowCounts` is set, the jitter hash sum `g_noiseAcc` (2-3 `noiseHashRaw` adds, split into separate `+=`/`-=` so 32-bit differences never wrap before widening) when `g_noiseIncremental` is set, and the incremental ML accumulator `g_mlAcc` (2-3 piece-square weight adds/subtracts via `mlSqW`/`mlSqB`) when `g_mlIncremental` is set. |
| `board_analysis.cpp` / `board_analysis.h` | Chip counting, row-level chip difference, one-step win detection (`findWinWhite/Black()`, `canWinWhite/Black()`), and `capacityWhite/Black()` (Lemma B remaining-advancement sums; analysis helpers, not eval weights -- the capacity advantage is linearly dependent on chip + forward, see `tests/test_eval.cpp`'s identity test) |
| `ai_eval.cpp` / `ai_eval.h` | Pluggable board evaluators. A registry `g_evaluators[]` (with `g_evalCount`) lists each `EvalDef` (name, parameter list of `EvalParamDef{name,key,def,lo,hi}`, scoring `fn`). Heuristics shipped: `evalClassic` (original heuristic: near-end win detection at rows `SIZE-2`/`1`, turn bonus, wall/column structure bonuses, chip-diff base), `evalExperimental` (Classic plus a "Forward" weight (rewards pieces further toward the goal), identical to Classic when that weight is 0), and `evalAdvanced` (Experimental plus 11 more terms in the fixed `ADV_*` slot layout, paramCount 16, weights may be negative: Support = diagonal same-color pairs under a `structOwner`-style single-ownership convention (merges the todo's defended-pieces + phalanx ideas, Lemma C geometry); Center = forwardness x file centrality; Mobility = per-piece legal-move count; Hole = D10 outpost-admitting back-rank columns; Control = occupancy of the two rows nearest the opponent's home row; Open = files empty on the own half but enemy-occupied; Race = closest-piece distance differential; Overext = advanced pieces with no diagonal-behind defender; Noise = two seeded-random forms selected by sign (param NoiseSeed = the seed, both deterministic per seed): Noise > 0 is the random piece-square table (per-(color,square) values in [-n,+n]; a strength weight whose board total scales with piece count -- theory 20 measured it badly at material scale), Noise < 0 is the bounded per-position jitter of magnitude -n (raw hash sum over occupied squares via `noiseHashRaw`/`noiseRawScan`, read as `(raw mod 2n+1) - n`; the leaf returns `realEval * ADV_JITTER_SCALE(256) + jitter`, so it provably reorders only EXACT eval ties -- the developer's tie-only construction, verified by the dominance walk in `test_eval.cpp`); RaceWin (0/1) = the exact D9/D14 decided-race sentinel detector (`raceWinCheck`), side-to-move aware with a one-tempo margin for the non-mover, returning `WhiteWin`/`BlackWin` exactly like `nearWinCheck`. Advanced is registered AFTER LearnedValue so persisted evaluator indices stay stable). Race/RaceWin are leaf terms fed by row extremes (from `g_rowCountW/B` counters during an incremental search, by board scan otherwise), NOT part of `g_evalPos`; the jitter (Noise < 0) is likewise a leaf term with its own accumulator (`g_noiseAcc`, seeded/latched by `evalBeginSearch` under `g_noiseIncremental`, maintained by make/unmake with 2-3 hash adds -- kept as separate += / -= statements because a combined 32-bit `(a - b)` wraps before widening to the 64-bit accumulator); every other Advanced term lives in the `evalPosFull`/`evalPosLocal` pair (per-square deltas; a mobility+overext bounding-box sum; hole/open affected-column recomputes). Zero-weight gating: `evalBeginSearch` leaves `g_evalIncremental` off when every positional weight is 0 (`posWeightsActive`, which counts Noise only when > 0) and enables `g_evalRowCounts`/`g_noiseIncremental` only when their terms are enabled, so unused machinery costs nothing (the chip-count-study fix; ladder-verified v2->v3 ~0% at w0,l0). **Turn weight (`p[0]`) is inert in a fixed-depth search.** `evalLeaf` adds `+p[0]` when White is to move and `-p[0]` when Black is, with no board dependence, so at a fixed depth every leaf shares one ply parity and gets the same constant -- which shifts every subtree value equally and changes no min/max comparison. It goes live only at mixed leaf parity (quiescence on, or `keepPartial` keeping a cut iteration), and it still affects displayed evals. So two IDs differing only in `t` are the same player for a bare fixed-depth agent, and ratios involving `t` are meaningless (the hill climber pins `t` rather than searching it). Details: `Docs/terminology.md`, "Turn weight". `evaluateBoard(turnColor, evaluator, params)` dispatches by index; a convenience overload `evaluateBoard(turnColor, turn, chip, wall, col)` calls Classic. `MAX_EVAL_PARAMS` is defined in `globals.h` so param-array callers need only that header. To add an evaluator: append one `EvalDef` and write its `fn` -- both UIs pick it up automatically. End-row win detection is handled before calling this. **Incremental eval:** for the minimax hot path, the positional part (structure + forward) is cached in `g_evalPos` instead of rescanned per leaf. `evalBeginSearch`/`evalEndSearch` (RAII-guarded in minimax) seed/tear it down; `evalPosFull` does the full scan; `evalPosLocal` computes a move's true neighbor-local delta (via `neighborStruct`, the orthogonal same-color pairs touching the two changed squares under `structOwner`'s single-ownership convention, plus those squares' forward score) applied by `simulateMove`/`unsimulateMove`; `evalLeaf` combines `g_evalPos` with the already-incremental `g_chipDiff` and turn term. An `EvalDef.incremental` flag opts in (requires the standard `p[0]=turn,p[1]=chip,p[2]=wall,p[3]=column,p[4]=forward` layout); non-incremental evaluators fall back to a full `evaluateBoard` at the leaf. The benchmark-only `g_evalLevel` selector reconstructs older leaf generations for speed measurement: level < 3 forces `g_evalIncremental` off in `evalBeginSearch`, and level 1 makes `evalLeaf`'s fallback use the full-board `chipDiff()` rescan instead of `g_chipDiff` (see `Docs/benchmarking.md`). `nearWinCheck` is shared so the fast and full paths can't diverge. `immediateEvalForDisplay(isMiniMax, evaluator, params)` returns a white-centric static eval of the current board for the UIs (a MiniMax side uses its own evaluator/weights; others fall back to Classic registry defaults). A third evaluator `LearnedValue` (`p[0]` = model slot, `p[1]` = Risk: for a DistModel slot, adds `(p[1]/10)*sigma` to the mean before the tanh squash (tenths of sigma, e.g. `p[1]=5` -> k=0.5), default 0 = mu-only, see `mlValueScoreRisk`) delegates to `mlValueScoreRisk` (see `ml_eval.cpp`); `nearWinCheck` is now declared in `ai_eval.h` so the learned evaluator and 1-ply explorers reuse it. **Incremental ML eval:** when the LearnedValue slot holds a sparse piece-square model (feature v2), `evalBeginSearch` also calls `mlIncrementalBegin` (recognizing LearnedValue by its own fn pointer, no agents.cpp dependency), `evalLeaf` short-circuits to `mlLeafScore` while `g_mlIncremental` is set, and `evalEndSearch` calls `mlIncrementalEnd`; LearnedValue's registry `incremental` flag stays false because that flag drives only the heuristic `g_evalPos` path. A v1 model in the slot leaves the ML path off and falls back to the full scan per leaf, and so does a nonzero Risk weight on any model: the sigma head is never accumulated, so `evalBeginSearch` skips `mlIncrementalBegin` whenever `p[1] != 0` and every leaf takes the full-scan `mlValueScoreRisk` path instead. |
| `ai_random.cpp` / `ai_random.h` | Three random AI strategies (`pureRandomMove`, `tieredRandomMove`, `smartRandomMove`), the scripted opening-sequence logic (`playOpenerWhite/Black`), and the pluggable **opener registry** `g_openers[]` (`OpenerDef{name, idName, desc, hasArg, hasArg2, argLabel, fn}`, `openerIndexByIdName`): opening-phase move sources an agent selects via `AgentSpec::openerKind`/`openerArg`/`openerArg2` and its `.opener(<idName>,<label>=<arg>[,ply=<arg2>])@N` ID segment. Three registered: `rand` (random for the agent's first `arg` plies), `book` (an opening/refutation-book follower: plays the stored reply from `models/book<arg>.txt`, keyed by `positionKey(sideToMove,false).hash`, at ANY ply the position matches unless capped by the optional `arg2` ply cutoff, then hands off; loads the book lazily once per process; ignores a stored move that fails bounds/`tryMoveQuick*`; the book file is NOT hashed into the agent ID so it is treated as immutable, a regenerated book gets a new slot), and `cbook` (the fuzzy generalization of `book`: `openerClusterBook` loads `models/cbook<arg>.txt` (an `MlcBook`, `src/ml_cluster.h`) lazily and cached the same way, then for the live position computes its v2 feature vector, XORs it against the book's own recorded start vector, canonicalises the difference under the left-right mirror (`mlcCanonical`), finds the nearest cluster for the current half-move bucket (`mlcNearest`), un-mirrors that cluster's move list if the canonicalisation flipped, and intersects the result with the position's ACTUAL legal moves (`generateMoves`). A non-empty intersection sets `globals.h`'s `g_useRootFilter` + `g_rootMoveWhitelist[]` to that intersection and returns `false` (never plays a move itself -- it narrows the search's root move list and lets the agent's own budgeted alpha-beta search choose among the survivors, the "filter mode" translation of Steinmetz & Gini's SMARTSTART paper from MCTS to alpha-beta). An empty intersection (the matched cluster's suggestions are all illegal here) returns `false` with the flag left off, the required safeguard against ever leaving zero legal root moves. Same optional `arg2` ply cutoff as `book`, for the same reason: clustering runs independently per half-move bucket, so a book mined to a deeper ceiling is a strict superset of a shallower one and one file serves every candidate ply window. Draws no `rand()`, so `rankAgentIsDeterministic` does not list it as stochastic.) Consulted only by the ranking game-runners that track a per-agent ply count (`playOneGame`, `playoutCapture`, and bookgen's/cbookdump's own replay loops), so an opener fn takes `ownPly` rather than reading global state. Those same callers reset `g_useRootFilter = false` unconditionally right after each move, so a `cbook`-narrowed root list can never leak into a later ply. Add one = a table row + fn. |
| `ai_minimax.cpp` / `ai_minimax.h` | Alpha-beta minimax: `miniMaxWhite/Black()` top-level search, `maxAlphaBeta`/`minAlphaBeta` recursive pruning, capture-first move ordering, win-decay for fastest wins. After the root move loop each side stores its best-line score (root `alpha`/`beta`) into `g_downEvalWhite`/`g_downEvalBlack` for the "predicted downstream" display (free: the value was already computed). **Budgets & telemetry:** with a per-move node budget (`g_nodeBudget`) or wall-clock budget (`g_timeBudgetMs`) set, the search runs iterative deepening (`searchRootWhite/Black` per depth) sharing one pool; `budgetTripped()` flags a cut leaf. Each search records `g_lastEffDepth` (fractional: completed depth + fraction of the cut iteration's root moves), `g_lastBudgetKind` (node/time/depth) and `g_lastNodes`/`g_lastLeafs`. A cut iteration is discarded unless `g_keepPartial`. **What `g_keepPartial` adopts is not a depth-d value.** `searchRootWhite`/`Black` do NOT stop when the budget trips: they keep walking the remaining root moves, and `budgetTripped` short-circuits each one to a static `evalLeaf` taken one ply in with no reply searched. Those scores are biased high for the side to move, so they can win the `a > alphaPrev` adoption test on merit they do not have. Measured on `model=169` at `nodes=200k`, 279 budget-limited plies: 62.0% no adoption, 19.4% adopted a genuinely searched root move, 18.6% adopted a post-cut static one, so half of all adoptions rest on an unsearched score (`plans/budget-parity-results-2-steady-meridian.md`). `g_lastPartAdopt` records which of the three happened (0/1/2), via the file-static `s_rootBestIdx`, the root-scan index of the move that last raised alpha. **The root is not ordered**: `orderMoves` runs only at interior nodes, so a partial iteration covers an arbitrary geometric slice of the root moves, not a promising one. **A second, less obvious thing rests on the same fact**: root candidates are always visited in board-geometry order, so an equal-scoring tie is always broken the same way regardless of what the transposition table holds. That BOUNDS the table's influence on a deterministic agent's reply, which is what lets `rankSchedule`'s `pairGameTarget` cap a deterministic pair at 2 games rather than replaying it. It does not by itself make the reply independent of the table: interior-node ordering IS table-driven, and `ttProbe` does not check `e.gen`, so a search reads entries its own earlier searches left and whether those survived depends on what else stored into their slots. That the reply does not move anyway is measured, not argued (theory 71, 2026-09-09): 1,836 replay-games with one side going silent, across node budgets from 200k to 8m and both silent-window shapes, 0 divergences, plus `rank.exe determinism` 280/280 subject-colours over the whole deterministic roster. Ordering the root would remove the bound, so rerun `tests/test_determinism.cpp` if you do, and expect the 2-game cap to need revisiting. `g_nodesAtDepth[d]` (bound `MAX_PROFILE_DEPTH`) records the cumulative node count when depth d finished, 0 if it never did, so the cost of one iteration is `g_nodesAtDepth[d] - g_nodesAtDepth[d-1]`; measured, the last completed iteration is 64-83% of everything spent to reach it, alternating with ply parity. **`g_iterMinRemain` (the `rem=N` head flag) is the node counterpart to `nextIterationFits`**: decline to start another iteration unless at least N% of the node budget is unspent. It is a static threshold rather than a prediction so the setting lives in the agent's ID, and it is inert at 0 and inert with no node budget. **`retain` (the `retainBudget` spec field, `g_nodeCarry[2]` in `globals.cpp`)** banks whatever a move leaves unspent and adds it to the SAME side's cap on its next move, so the budget is conserved per game (total <= cap x plies) rather than per move, and an individual move may spend several caps' worth. The purse lives in `agentChooseMove`, which reads it before the search and writes it back from `g_lastNodes` afterwards, indexed 0=White/1=Black so both agents in a game keep their own. It must be cleared per game by `retainResetCarry()` for the same reason `ttClear()` is, since cross-game state makes play depend on shard order. `ranking.cpp` calls it beside every per-game `ttClear`, and `agreeStep` parks the polled agent's purse in `s_agreeOthCarry` so the probe cannot spend the driver's savings. Measured with `rem=70,nodes=200k`: the chip counter goes from 108,032 to 165,058 mean nodes/move with a 429,035 peak, and plies completing depth 7 or more go from 19.7% to 36.8%. **`retain` governs TWO independent purses.** With a wall-clock budget it banks unspent MILLISECONDS in `g_timeCarry[2]` instead, read and written by the same `agentChooseMove` block against `g_lastSearchMs` (the time analogue of `g_lastNodes`, written at both top-level search exits from `elapsedMs()`). An agent may carry a node budget, a time budget, or both, and each purse banks only its own remainder, so a node-only `retain` agent never touches `g_timeCarry` and vice versa. `retainResetCarry()` clears both, and `agreeStep` parks both. The wall-clock purse exists because `nextIterationFits` DECLINES an iteration it predicts will not fit, which leaves the tail of a time budget unspent for the same reason `rem=N` does on the node side, and it is why a time-budgeted search finishes at roughly 40% of its allowance. `retain` is inert only when the agent has neither budget. **A wall-clock budget is enforced by three cooperating mechanisms, and the first is the load-bearing one.** (1) `s_timeExpired` is STICKY: the first node to find the deadline past latches it, and every later node in that search returns immediately without re-reading the clock. Without the latch the budget bounded almost nothing, because a node that observed the deadline could return true while the other nodes in its sampling window never asked and recursed to full depth anyway. (2) `TIME_CHECK_MASK` samples `steady_clock::now()` once per 256 nodes rather than 4096, sized from measurement rather than guess: `now()` costs 22.1 ns against a 0.183 ns empty-loop iteration, so at ~270 ns/node a 256-node interval costs 0.086 ns/node (under 0.04%) and bounds the granularity at about 69 us, under 0.05% of a 150 ms budget. (3) `nextIterationFits(prevIterMs, lastIterMs)` is a predictive pre-iteration check: iterative deepening declines to START a depth whose projected cost exceeds the time left, since a plain "is the deadline past" test never fires at the moment the decision is made. The growth factor comes from the search's OWN last two iteration times and the check ABSTAINS until two have been measured, never from an assumed per-ply constant, because branching depends on the evaluator's move-ordering quality and does not transfer between cores. Node budgets are deliberately excluded from the predictive check: a node budget is exact and needs no forecast. The consequence to know when reading realized timings is that a time-budgeted search finishes at roughly 40% of its allowance (measured 40.4 / 39.0 / 40.2% at 50 / 150 / 450 ms on a chip counter), because the last iteration it declines to start would have cost more than the remainder. Pre-fix behavior and its measured 3.9x to 7.1x overshoot: `TIME BUDGET NOT ENFORCED`, `Docs/corrections.md`. **Opt-in, ablatable efficiency features** (default off, so console/GUI/tests are unchanged): `g_useAlphaBeta` (off = full minimax baseline), `g_aspirationWindow` (root window seeded from the prior iteration), `g_useTT`/`g_useMoveOrder`, which route to `maxAlphaBetaOrdered`/`minAlphaBetaOrdered` (transposition probe/store keyed by `positionKey` + best-move/killer/history ordering), and `g_useQuiescence` (`quiesceMax`/`quiesceMin`: a captures-only stand-pat extension entered at true depth leaves of both search paths, terminating because captures strictly shrink material, capped by `QS_MAX_PLY`; quiescence nodes count against the node budget, and the qnode-entry canWin checks + win-decay keep the leaf sentinel semantics). **Root-move filter** (`globals.h`'s `g_useRootFilter`/`g_rootMoveWhitelist[]`, the `cbook` opener's mechanism, `src/ai_random.cpp`): `searchRootWhite`/`searchRootBlack`'s `tryMove` lambda checks `rootMoveAllowed(x,y,z)` first and skips (without counting toward `rootTotal`) any candidate not on the whitelist when the flag is set, so the node/time budget goes deeper on fewer root moves. Root-only: the recursive `maxAlphaBeta`/`minAlphaBeta` never consult it, matching how every opener only ever decides the current ply. `test_ai_integration.cpp` asserts these features preserve the exact search value (tt/ord with and without qs), that qs resolves a leaf exchange a plain depth-1 search misses, and that the root filter both changes the node count and constrains the chosen move to the whitelist. |

## Modular ML system (linked into every target; see `ML.md`)

The ML system is four pluggable axes plus an agent composition. An **Agent** is a **Move Chooser** that is either a **Search** (**Explorer** + **Evaluator**) or a **Policy** (a direct chooser, heuristic or a learned move-rater). Each axis is a registry of `*Def` structs (name + metadata + fn pointer), so adding one is a single table entry + a function body, and the console/GUI/tournaments/docs all pick it up.

| File | Purpose |
|---|---|
| `ml_features.cpp` / `ml_features.h` | Board reading for ML. `generateMoves(side, Move*)` (capture-first, shared by explorers/policies/trainer). Value features v1 (`mlExtractValueFeatures`, `MLV_FEATURES=30`, white-centric dense aggregates) and v2 (`mlExtractValueFeaturesV2`, `MLV2_FEATURES=129`, sparse piece-square: one binary input per color+square via `mlSqW`/`mlSqB`, plus `MLV2_STM=128` side to move; a move changes 2-3 inputs, the locality the incremental `g_mlAcc` accumulator exploits). Move features (`mlExtractMoveFeatures`, `MLM_FEATURES=9`, side-relative) for policy models. Names tables (incl. `mlValueFeatureNameV2`) drive the auto-doc. |
| `ml_cluster.cpp` / `ml_cluster.h` | Fuzzy nearest-cluster opening-book machinery, feeding the `cbook` opener (`src/ai_random.cpp`) and `rank.exe cbookdump`/`cbookfit` (`src/ranking.cpp`). Applies Steinmetz & Gini's SMARTSTART (IJCAI 2015: cluster professional Go positions per move-number, match the live position to its nearest cluster) to Breakthrough, with two adaptations the 8x8 board and alpha-beta search require. (1) **Clusters the XOR difference from the start board, not the raw position.** A raw v2 board vector fails here: two same-ply Breakthrough positions still share ~30 of 32 pieces, so cosine similarity between them sits near 1 regardless of content and spherical k-means has no angular signal to separate on, unlike Go where a move-20 position's ~20 stones on 361 points barely overlap between games. `MlcVec` is a 128-bit 0/1 vector (`MLC_DIM=128`, the v2 piece-square layout minus side-to-move, which is redundant with half-move parity). `mlcBoardVector`/`mlcDiff` read the live board and XOR it against a stored start vector, which is sparse in exactly the paper's own regime (roughly 16-24 bits set at half-move 8-12). (2) **Filters the search's root move list rather than biasing MCTS playouts**, alpha-beta's analogue of the paper's own filter mode: a compute-for-depth trade instead of a compute-for-breadth one (see `globals.h`'s `g_useRootFilter`). **Left-right canonicalisation** (`mlcCanonical`, reusing `ml_train.cpp`'s `mlv2MirrorIndex` mapping as `mlcMirrorIndex`): folds every position onto the lexicographically smaller of itself and its mirror before clustering, halving the space exactly (sound because the rules and standard start are left-right symmetric). The opener un-mirrors a matched cluster's moves back before checking legality. Colour-swap symmetry does NOT apply (it would require an unreachable side-to-move/move-count combination at a given half-move) and is never used. **Spherical k-means** (`mlcSphericalKMeans`): unit-normalize each 0/1 point (`1/sqrt(popcount)`), assign by cosine similarity (a dot product against a unit centroid), re-normalize each centroid as the mean of its members, k-means++ seeding + farthest-point reseeding of any cluster that empties, its own LCG (`lcgNext`) rather than `rand()` so clustering never perturbs the ranking replay's `srand()` stream. `mlcEffectiveK(k,n,minPerCluster)` caps K by density (`MLC_MIN_PER_CLUSTER=32`) so a thin bucket degrades to fewer, better-supported clusters instead of near-singletons. **Book structures**: `MlcBook` (a `start` vector + per-ply `MlcBucket`s), `MlcBucket` (ply, point count, `MlcCluster`s), `MlcCluster` (unit-norm centroid, size, mean intra-cluster cosine, count-sorted `MlcMove` list, already truncated to `--keep` at fit time). `mlcNearest` picks a bucket's best-matching cluster (ties resolve to the first, which is deliberate for the degenerate all-identical-points ply-0 bucket, where every game starts from the same position). `mlcSaveBook`/`mlcLoadBook` read/write `models/cbook<N>.txt` (sparse per-cluster centroid lines, so an early bucket's mostly-zero vector doesn't bloat the file). Pure and dependency-free (no `rand()`, no board globals except via `mlcBoardVector`'s read), unit-tested in `tests/test_ml.cpp`. |

## AI Player Types (`PlayerEnum`)

| Value | Name | Description |
|---|---|---|
| 0 | Human | Console input. Move format `c1d` (source col, source row, dest col). |
| 1 | UniformRandom | All legal moves equally likely |
| 2 | TieredRandom | Prioritizes winning moves first, then captures, then normal moves |

| Value | Name | Description |
|---|---|---|

## Architecture Notes

- **Simulate/unsimulate pattern:** `simulateMoveWhite/Black` and `unsimulateMoveWhite/Black` apply and reverse moves in-place so minimax avoids copying the board. They also maintain incremental state across make/unmake: piece counts, `g_chipDiff`, `g_whiteAtEnd`/`g_blackAtEnd`, and (during an incremental search) the positional accumulator `g_evalPos`.
- **Incremental evaluation:** a move only changes 2 squares, so instead of rescanning all 64 at each leaf, the positional score (structure + forward) is kept in `g_evalPos` and updated by each make/unmake via a true neighbor-local delta (`evalPosLocal`). Like the `g_chipDiff` counter, it touches only what the move changed: `neighborStruct` sums the orthogonal same-color pairs of the two changed squares (under `structOwner`'s single-ownership convention, so it matches `evalPosFull` exactly and excludes the same top-row-wall / rightmost-column pairs), and the forward term is just those two squares' per-square score. No region is rescanned. The leaf (`evalLeaf`) then just adds the already-incremental `g_chipDiff` and the turn term. Seeded/torn down per search by `evalBeginSearch`/`evalEndSearch`. Guarded by an equivalence test (`test_eval.cpp`) that walks the move tree and asserts `g_evalPos` always equals a full `evalPosFull` recompute.
- **Two validation tiers:** `tryMoveWhite/Black` gives full validation with user-readable error messages for human input. `tryMoveQuickWhite/Black` skips bounds checks for AI inner loop performance.
- **Capture-first move ordering:** In minimax, moves for each piece are tried in strict priority order: actual captures (diagonal to an enemy piece), then empty diagonal advances, then the forward move. This ordering maximizes alpha-beta cutoffs. End-row win detection (`canWinWhite`/`canWinBlack`) uses `g_whiteAtEnd`/`g_blackAtEnd` for O(1) checks instead of scanning a row.
- **Win decay:** When minimax finds a forced win, the score decreases by 1 per level, incentivizing the fastest possible victory path.
- **Evaluator registry / parameter threading:** Instead of fixed positional weights, the chosen evaluator (`int evaluator`) and its parameter array (`const int* evalParams`) are threaded together through `moveWhite/Black` -> `miniMaxWhite/Black` -> `maxAlphaBeta`/`minAlphaBeta` -> `evaluateBoard`. Adding/renaming a parameter or evaluator is a one-place edit in `g_evaluators` (`src/ai_eval.cpp`); both the console (`getEvaluatorSettings`) and GUI (`DrawPlayerConfig`) generate their controls from that table.
- **`minimax_params.txt`:** Key-value config file (`key=value`, `#` comments) for persisting preferred AI settings between sessions. Per side: `<side>_eval`, `<side>_depth`, `<side>_opener`, and one key per evaluator weight (`<side>_<key>`, with legacy `<side>_<key>_weight` still honored).
- **Section banners:** The longer source files (`moves.cpp`, `ai_random.cpp`, `settings.cpp`, `gui/main_gui.cpp`) carry `// === LABEL ===` banner comments before each logical section, so `grep "// ==="` over a file returns its outline and `grep "// === FAST VALIDATION"` jumps to a region. Labels mirror the per-file descriptions in this document. `main_gui.cpp` also lists the sections in its header comment. Keep banners in sync when adding or moving a section. Vendored headers (`tests/catch.hpp`, `gui/raygui.h`, `third_party/...`) are excluded.
- **Engine link set:** the `ml_features.cpp` / `ml_model.cpp` / `ml_eval.cpp` trio is required by the engine (ai_eval.cpp's `LearnedValue` evaluator calls `mlValueScore`), so every build target (`breakthrough.exe`, GUI, web, tests) links them. `ai_minimax.cpp`'s opt-in transposition-table path also pulls in `src\datastore.cpp` (for `positionKey`) and `src\transposition.cpp`, so every target links those two as well (they are inert unless an agent sets `useTT`). `ml_cluster.cpp` joined this required set on 2026-08-26: `ai_random.cpp`'s `cbook` opener calls its clustering/matching functions directly, and `ai_random.cpp` is itself in every target's link line, so a target missing `ml_cluster.cpp` fails to link rather than merely misbehaving at runtime.
